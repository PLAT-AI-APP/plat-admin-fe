# 운영 처리 기준 (클로즈베타 초안)

콘솔로 신고·문의·환불·보상을 처리하는 사람이 보는 문서다. **법에서 기한이 정해진 것**은 그대로 따르고,
나머지 기한(표의 `확인 필요`)은 운영 책임자가 정해 이 문서를 고친다.

## 0. 매일 확인

| 어디서 | 무엇을 |
|---|---|
| 헤더 벨·사이드바 뱃지 | 답변 대기 문의(Q&A), 신고된 채 노출 중인 댓글, 검토 대기 신고 건, 발송 대기 상품권 교환 |
| Slack 운영·오류 채널 | 아래 "Slack 알림" 표. 특히 새 1:1 문의, 새 신고 건, 환불 기한 임박, 상품권 교환 신청, 결제 지급 중단 |
| 대시보드 | 어제 대비 가입·대화·결제·크레딧 사용. 급변하면 원인을 본다 |
| AI 운영 > AI 원가 | 원가·매출(부가세 제외)·마진율, 원가 상위 유저. 한 유저가 원가를 몰아 쓰면 대화 내역·결제를 확인한다. 무료 크레딧 사용이 많은 베타에서는 마진이 낮게 나오는 것이 정상이다 |

알림 제목 앞의 `plat-be-prod-*` / `plat-be-dev-*`(뒤에 `-api`·`-ai`·`-batch`·`-admin`)로 어느 서버·앱의 알림인지 구분한다.

| 🔴 | 제작자 수익 대사 불일치 | 개발 채널로. 의심 계정은 먼저 동결 |
| 🔴 | AI 제공사 크레딧 소진 / 인증 실패 / 모델 사용 불가 | 8장. 같은 오류는 10분 동안 다시 알리지 않는다 |
| 🔴 | [Mail Server] 메일 발송 실패 | 인증·결제 메일이 안 간 사용자가 있을 수 있다. 문의 오면 재발송 안내 |
| 🔴 | 그 밖의 오류(5xx, DB, 미처리 예외)·서버 기동/종료 | 개발 채널로. 기동·종료는 배포 때 정상 |

## 1. 신고

### 우선순위와 기한

| 사유 | 첫 판정 기한 | 비고 |
|---|---|---|
| 미성년자 성적 콘텐츠 (`MINOR_SEXUAL`) | **즉시(발견 당일)** | 대상 조치 + 피신고자 영구 정지를 기본으로 검토. 필요하면 수사기관 신고(방송통신심의위원회·경찰청) |
| 명예훼손·사생활 침해 (`DEFAMATION`) | 접수 후 지체 없이 — 아래 임시조치 절차 | 정보통신망법 제44조의2 |
| 개인정보 노출 (`PERSONAL_INFO`) | 당일 | 노출된 정보를 먼저 가린다(댓글 숨김·세계관 삭제) |
| 실존 인물 사칭 (`IMPERSONATION`) | `확인 필요`(권장 2영업일) | |
| 그 밖의 사유 | `확인 필요`(권장 3영업일) | |

### 판정

- **조치함**은 대상 조치(댓글 숨김·세계관 삭제) 또는 피신고자 제재가 하나 이상 있어야 닫힌다. 없으면 **위반 없음**.
- 닫힌 케이스는 다시 열리지 않는다. 같은 대상이 다시 신고되면 새 케이스가 되고, 상세의 "지난 케이스"에 이력이 보인다.
- 처리 메모는 제재 사유로 유저에게 남는다. 확인 가능한 근거로 쓴다.
- **AI 답변 신고**: 먼저 스냅샷(신고자 메시지 + AI 답변)만으로 판단한다. 대상 조치는 없다 — 유도된 답변이면 위반 없음,
  세계관 설정이 원인이면 제작자 제재 또는 해당 세계관 신고 건으로 조치한다. 프롬프트·모델 문제는 개발 채널로 넘긴다.

### AI 답변 신고의 앞뒤 대화 열람

신고 상세의 **앞뒤 대화 보기**는 신고된 답변 앞뒤 5개씩, 신고자의 실제 개인 대화를 연다. 원칙:

1. **스냅샷으로 판단이 안 될 때만 연다.** "유도됐는지", "앞 맥락에서 설정이 어떻게 흘렀는지"를 봐야 하는 경우다. 호기심·확인 차원으로 열지 않는다.
2. `report:read` 와 `chatExport:read`(대화 반출) 두 권한이 모두 있어야 열린다. 직책에 대화 반출 권한은 신고 담당 중 필요한 사람에게만 준다.
3. **열람은 기록된다.** 누가 어느 케이스의 대화를 언제 열었는지 관리자 활동 로그에 "신고 대화 맥락 열람"으로 남는다.
   열었다면 처리 메모에 열람 이유를 한 줄 쓴다(예: "유도 여부 확인 위해 앞 대화 열람").
4. 본 내용을 콘솔 밖(메신저·스크린샷·문서)으로 옮기지 않는다. 처리 메모에도 대화 원문을 붙이지 않고 판단 근거만 요약한다.
5. 서버는 관리자 화면의 응답 본문을 접근 로그에 남기지 않는다. 그래서 열람 기록은 활동 로그 하나뿐이다.
6. 방이 이미 지워졌으면 "대화 없음"으로 나온다. 그때는 스냅샷으로만 판단한다.

### 임시조치 (정보통신망법 제44조의2)

권리를 침해당했다는 사람이 삭제를 요청하면:

1. 요청자와 침해 내용을 확인한다(신고 상세·1:1 문의).
2. 판단이 어렵거나 다툼이 예상되면 **30일 이내 임시조치** — 댓글은 숨김으로 내린다.
   세계관은 콘솔에 "숨김"이 없고 삭제만 있다 → 삭제 전에 운영 책임자 확인. (`확인 필요`: 세계관 임시 비공개 기능 필요 여부)
3. 게시자에게 조치 사실을 알린다(1:1 문의 답변 또는 이메일).
4. 게시자가 이의를 제기하면 재검토하고, 30일 안에 결론이 없으면 원칙대로 처리한다.
5. 처리 과정을 신고 케이스 메모에 남긴다.

## 2. 1:1 문의

| 유형 | 답변 기한 | 비고 |
|---|---|---|
| 환불 (`REFUND`) | 아래 3장 | 환불 요청으로 자동 생성된다. 유저가 직접 쓸 수 없는 유형 |
| 결제·계정 | `확인 필요`(권장 1영업일) | |
| 버그 (`BUG`) | `확인 필요`(권장 2영업일) | 베타 안내 띠의 "버그 제보"가 이 유형으로 연다. 재현되면 개발 채널로 |
| 그 밖 | `확인 필요`(권장 2영업일) | |

- 답변은 사람이 쓴다. 환불 결과를 문의 답변에 자동으로 붙이지 않는다(환불 화면에서 처리하고, 답변에는 안내만 쓴다).
- 답변에 다른 유저의 개인정보를 쓰지 않는다.

## 3. 환불 (전자상거래법 제18조)

- 청약철회로 환불이 확정되면 **3영업일 이내에 환급**해야 한다. 늦으면 지연 이자 대상이 된다.
- 현재 정책: 노트를 하나도 쓰지 않은 결제만, 결제 후 7일 안에 전액 환불. (정책 자체는 법무 검토 중 — D7)
- 처리 순서: 유저가 환불을 신청하면 환불 문의가 생긴다 → 결제 내역 → 해당 주문 상세 → **환불 승인**(또는 거절).
  문의 화면의 환불 블록과 승인 확인 문구에 "신청 뒤 노트를 썼는지"가 보인다 — 썼으면 승인해도 서버가 거절한다.
  승인하면 PG 취소가 나가고, 신청 뒤 노트를 쓴 경우는 서버가 자동으로 거절한다. **신청일부터 3영업일 안에 승인까지 끝낸다.**
- PG 쪽에서 이미 취소했는데 서버에 반영되지 않았으면 주문 상세의 수동 취소 기록(경위 필수)을 쓴다.
- 실패하면 주문 상태와 Slack 알림을 보고 다시 실행한다. 이미 끝난 환불은 두 번 실행되지 않는다.
  노트 회수 중 DB·통신 같은 일시 오류가 나면 환불은 "처리 중"으로 남고 재개 배치가 몇 분 안에 다시 시도한다 — 바로 다시 누르지 않아도 된다.
- **강제 환불**은 기한·사용 여부를 건너뛰고 돈을 전액 돌려준다. 이미 쓴 노트는 회사 손실이다. 분쟁 무마 등 운영 책임자가 정한 경우에만,
  별도 권한(`refundForce:adjust`)을 가진 사람이 내부 사유를 적고 쓴다. 실행하면 Slack 에 남는다.

## 4. 보상·크레딧

- 한 명: 크레딧 조정 → 크레딧 조정. 한 번에 100,000 까지. 사유에 CS 티켓 번호처럼 확인 가능한 근거를 쓴다.
- 여러 명(베타 보상·장애 보상): 크레딧 조정 → **일괄 지급**. 한 번에 500명, 한 명당 100,000까지.
  - 결과에 실패한 유저가 있으면 **같은 모달에서** "실패한 유저만 다시 시도"를 누른다. 같은 묶음 키라 이미 받은 유저는 건너뛴다.
  - 모달을 닫고 새로 열면 새 묶음이 된다 — 같은 명단을 새 모달로 다시 보내면 **두 번 지급된다**.

## 5. 상품권 교환

- 발송은 사람이 한다: 수익 → 교환 요청에서 발송 처리 또는 반려(포인트가 돌아간다).
- 수익 포인트 지급·차감은 확인 창을 거치고 요청마다 새 멱등키가 붙는다 — 연타해도 한 번만 들어간다. 같은 조치를 다시 하려면 창을 새로 연다.
- 받는 번호는 발송에만 쓴다. 처리 30일 뒤 배치가 끝 4자리만 남기고 가린다 — 그 전에 발송 누락 문의를 마무리한다.
- 발송 대기 교환이 남아 있는 제작자는 탈퇴할 수 없다. 탈퇴 문의가 오면 발송·반려를 먼저 끝낸다.

## 6. 탈퇴·계정

- 탈퇴는 유저가 직접 한다. 계정은 익명화되고 대화·페르소나·댓글·만든 세계관이 지워진다. 결제 기록은 5년 보관된다.
- 같은 이메일은 7일 동안 재가입할 수 없다.
- 운영자는 "탈퇴" 상태를 넣을 수 없고, 탈퇴한 계정을 다른 상태로 되살릴 수도 없다(서버가 400 `USER_STATUS_CHANGE_INVALID` 로 막는다).
  정지·영구 정지를 쓴다. 기간 정지는 만료가 지금보다 뒤여야 하고, 회원 화면의 "영구 정지"는 만료 없는 정지로 걸린다.
- 부적절한 닉네임·소개·프로필 사진은 유저 상세 > 더보기 > **프로필 초기화**로 되돌린다. 닉네임은 `u{유저ID}`, 소개는 빈 값,
  사진은 삭제. 옛 값과 사유는 계정 정보 탭의 "프로필 초기화 기록"에 남고 유저에게 알림은 가지 않는다. 반복되면 정지를 건다.

## 7. 점검

점검은 두 가지다.

| 방법 | 언제 | 어떻게 |
|---|---|---|
| **서버 점검 예약**(권장) | 배포·DB 작업 등 계획된 점검 | 운영 → 서버 상태 → 점검 예약(`server:write`) |
| 사용자 웹 전체 점검 | 서버 예약으로 막을 수 없는 경우(예: 프론트만 문제) | plat-fe 배포 환경 변수 `NEXT_PUBLIC_MAINTENANCE_MODE=on` 으로 **다시 빌드·배포**. 끌 때도 재배포 |

서버 점검 예약의 단계:

1. **예고(`NOTICE`)** — 예약하면 앱이 점검 예정 시각을 안내한다. 이 단계에서만 **취소**할 수 있다.
2. **소프트 종료(`DRAINING`)** — `drainStartsAt` 부터 새 요청은 503(`SERVICE_MAINTENANCE`)으로 막고, 이미 시작된 흐름(결제 승인 확정, 채팅 답변 스트림)은
   통과시킨다. **결제 도중인 사람을 위해 10분 이상**을 둔다.
3. **점검(닫힘)** — `closesAt` 부터 완전히 닫는다. 현황 화면의 인스턴스별 진행 중 요청·답변 생성 수와 "결제창 열린 주문 수"가 0 에 가까운지 보고
   필요하면 **지금 닫기**로 앞당긴다.
4. **끝내기** — 작업이 끝나면 누른다. 인스턴스가 몇 초 안에 반영해 다시 연다. 소프트 종료 중에 누르면 종료를 멈춘다.

## 8. AI API 키 교체

AI 운영 → **API 키**(`/ai/keys`). 제공사(Anthropic·OpenAI·Google)마다 **메인·서브** 두 칸이 있다. 보기는 `server:read`, 저장·삭제·확인·메인 복귀는 `server:write`.

- 키는 AWS Parameter Store 에 저장되고 ai 서버가 **재시작 없이 몇 초 안에** 새 키를 읽는다. 화면·로그 어디에도 키 원문은 다시 나오지 않는다.
- 메인 키가 한도 초과·잔액 소진·인증 실패로 막히면 서버가 **자동으로 서브로 넘긴다**(Slack 🟡). 한도 초과는 1분 뒤 저절로 메인으로 돌아가고,
  잔액 소진·인증 실패는 사람이 되돌리거나 자동 확인이 메인을 다시 확인할 때까지 서브를 쓴다. 제공사 장애·과부하는 서브도 같은 서버라 넘기지 않는다.

교체 절차(정기 교체·유출 의심·만료 임박):

1. 제공사 콘솔에서 새 키를 만든다. 예산·한도를 확인한다.
2. **서브 칸에 먼저 저장**하고 **확인**을 눌러 연결을 본다. 만료일을 알면 함께 적는다(만료 전 Slack 알림).
3. 메인 칸에 같은 키(또는 새 메인 키)를 저장하고 **확인**한다.
4. 서브로 넘어가 있던 상태면 **메인 복귀**를 누른다. 넘어가 있지 않아도 눌러도 된다.
5. 대화가 정상인지 모델 테스트(AI 모델 관리 → 테스트 호출)로 확인한 뒤, 제공사 콘솔에서 옛 키를 폐기한다.
6. 메인 키는 지울 수 없다(`AI_KEY_MAIN_NOT_DELETABLE`) — 새 키로 덮어쓴다. 서브는 지울 수 있다.

잔액 소진(🔴 크레딧 소진)이면 먼저 제공사에서 충전하고, 충전이 반영되면 **메인 복귀**를 누른다.

## 9. 권한 운영 규칙

- **직책(권한 묶음)은 최고관리자만 만들고 고치고 지운다.** 그 밖의 관리자에게 직책 화면은 읽기 전용이다.
- 관리자 계정에는 **자기 권한의 부분집합인 직책만** 줄 수 있다. 더 넓은 직책의 계정은 만들거나 수정·비밀번호 초기화할 수 없다.
  비밀번호 초기화는 임시 비밀번호를 평문으로 보여 주므로 그 계정으로 로그인하는 것과 같다.
- 최고관리자 계정의 수정·삭제·잠금 해제·초기화는 최고관리자만 한다. 활성 최고관리자는 늘 둘 이상 두는 것을 권한다(마지막 한 명은 비활성·삭제·직책 변경이 막힌다).
- 누구도 자기 직책을 바꾸거나 자기 계정을 지울 수 없다.
- 권한은 요청마다 서버가 다시 읽는다. 직책에서 권한을 빼면 **바로** 적용된다(다시 로그인할 필요 없음). 계정을 비활성·삭제하면 세션도 끊긴다.
- 로그인 5회 실패로 잠기면 15분 뒤 저절로 풀린다. 급하면 다른 관리자가 관리자 관리에서 해제한다.
- 민감 권한은 필요한 사람에게만: 대화 반출(`chatExport:read`), 로그(`log:read` — 다른 관리자의 변경 값이 보인다), 강제 환불(`refundForce:adjust`),
  크레딧·수익 조정(`creditAdjustment:adjust`·`earning:adjust`), 서비스 관리자 부여(`serviceAdmin:write`), 서버·키(`server:write`).
- 2026-09 에 권한 코드 일부를 바로잡았다 — 약관 번역 삭제는 `legal:delete`, AI 모델 테스트 호출은 `aiModel:write`, 수익 적립 재실행은 `earning:adjust`,
  임시 저장 삭제는 `notice:delete`. **이 기능을 쓰던 직책에는 새 코드를 다시 줘야 한다.**
- 공지 게시·숨김은 `notice:publish` 가 있어야 한다. 작성(`notice:write`)만 있으면 임시 저장까지만 할 수 있다.
